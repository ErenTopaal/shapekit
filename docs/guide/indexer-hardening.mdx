Most of a transaction envelope is chosen by whoever submitted the transaction. stellar-core checks some of it, checks some of it only in part, and passes the rest through to the ledger unchanged. An indexer that trusts an unchecked field, decodes without limits, or reads participants from the envelope can store wrong data or stop ingesting on a single transaction.

This page covers, in order: which envelope fields core validates, field by field; depth, length and count caps that never refuse data the network could have produced; why participants come from transaction meta and not from the envelope; how to store every strkey form defined by [SEP-23](https://github.com/stellar/stellar-protocol/blob/master/ecosystem/sep-0023.md), including muxed and signed-payload addresses; and a checklist for auditing an indexer written in any language.

The field table, the caps table and the checklist are generated from the data files of [shapekit](https://github.com/ErenTopaal/shapekit/blob/v0.1.0/README.md), an open-source corpus of rare but valid Stellar ledger data with a replay harness for indexers. Every row cites the stellar-core v30.0.0, stellar-xdr v30.0 or soroban-env-host v30.0.0 source it was read from. The field table is checked against the shapekit corpus manifest, which records the corpus entries that exercise each field. "Protocol" on this page always means the protocol version of the ledger that holds the data.

This page assumes you already read ledgers, for example with the [Ingest SDK](/docs/data/indexers/build-your-own/ingest-sdk) or the [Token Transfer Processor](/docs/data/indexers/build-your-own/processors/token-transfer-processor). For how muxed accounts and memos are used by applications, see [Pooled accounts: muxed accounts and memos](/docs/build/guides/transactions/pooled-accounts-muxed-accounts-memos), and for converting between address types in the SDKs, see [Convert an address to other types](/docs/build/guides/conversions/address-conversions).

## Validated and unvalidated fields {#validated-and-unvalidated-fields}

The table below gives one of three answers for each field:

- **yes**: core rejects the transaction, or fails the operation, when the value is wrong.
- **partial**: core checks some properties of the value, or the check happens later inside the Soroban host and only on some paths.
- **no**: core passes the value through without looking at its content.

<Warning>

**A "yes" does not make a value true.** Many checks run when the transaction is applied, and they only fail that transaction or operation. A ledger still carries the failed transaction: `LedgerCloseMetaV2` holds the whole transaction set and one `TransactionResultMetaV1` per transaction with its result ([Stellar-ledger.x](https://github.com/stellar/stellar-xdr/blob/v30.0/Stellar-ledger.x#L587-L596), [LedgerCloseMetaV2](https://github.com/stellar/stellar-xdr/blob/v30.0/Stellar-ledger.x#L668-L690)). From protocol 13 core stops checking signatures of a transaction that already failed validation, so a failed transaction can carry signatures that were never verified ([`TransactionFrame::processSignatures`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/TransactionFrame.cpp#L1516-L1578)). Treat an envelope value as known good only when the transaction result and the operation result are successes.

</Warning>

### Fields core never checks {#fields-core-never-checks}

**Mux ids.** Core reduces every `MuxedAccount` to its ed25519 key with `toAccountID`, which drops the 64-bit id ([`toAccountID`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/TransactionUtils.cpp#L1184-L1201)). Outside tests, core copies the id into classic and Soroban events ([`makeMuxIDSCVal`, `makeMuxedAccountAddress`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/TransactionUtils.cpp#L2272-L2300)) and into its JSON output ([XDRCereal.cpp](https://github.com/stellar/stellar-core/blob/v30.0.0/src/util/XDRCereal.cpp#L114)), and compares it in one check: a clawback is malformed when its `from` equals the operation source, compared as whole `MuxedAccount` values, id included ([`ClawbackOpFrame::doCheckValid`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/ClawbackOpFrame.cpp#L63-L71)). The id is never looked up or stored in a ledger entry, so a mux id is any 64-bit value the submitter chose, with no account behind it. The only protocol rule about muxed accounts is their key type: before protocol 13 core rejects a transaction that contains any muxed account with `txNOT_SUPPORTED` ([`MuxChecker`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/TransactionUtils.cpp#L1305-L1347), [`TransactionFrame::commonValidPreSeqNum`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/TransactionFrame.cpp#L1254-L1264)).

**Memos.** `MEMO_TEXT` is limited only by its XDR type, `string text<28>`, which bounds bytes, not characters ([Memo](https://github.com/stellar/stellar-xdr/blob/v30.0/Stellar-transaction.x#L773-L785)). Core runs no UTF-8 or content check on it. `MEMO_ID`, `MEMO_HASH` and `MEMO_RETURN` are not checked either; a `MEMO_RETURN` hash need not name any transaction. Core copies the memo of a classic payment to a plain account into the `to_muxed_id` field of the transfer or mint event, as a string, a u64 or bytes depending on the memo type ([`makeClassicMemoSCVal`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/TransactionUtils.cpp#L2252-L2270), [`getPossibleMuxedData`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/EventManager.cpp#L104-L136)), so the same unchecked bytes reappear inside event data.

**Data entry values.** `ManageDataOp.dataValue` is up to 64 opaque bytes. Core copies it into the data entry as it is ([`ManageDataOpFrame::doApply`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/ManageDataOpFrame.cpp#L31-L102)).

### Fields core checks only in part

**Signed payloads.** A signed-payload signer key carries 1 to 64 payload bytes: the upper bound comes from XDR and core rejects an empty payload ([`TransactionFrame::commonValidPreSeqNum`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/TransactionFrame.cpp#L1285-L1293), [`SetOptionsOpFrame::doCheckValid`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/SetOptionsOpFrame.cpp#L308-L315)). The payload content is never checked.

**Soroban footprints.** Core limits the key types, key sizes and entry counts of a footprint and rejects duplicate keys, but the keys need not exist, and the host only enforces that the contract stays inside the footprint ([`TransactionFrame::checkSorobanResources`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/TransactionFrame.cpp#L792-L907), [`invoke_host_function`](https://github.com/stellar/rs-soroban-env/blob/v30.0.0/soroban-env-host/src/e2e_invoke.rs#L470-L578)). A footprint is what the submitter allowed a contract to touch, not what it touched.

**Soroban authorization entries.** Core never inspects auth entries; it serializes them and passes them to the Soroban host ([`invokeHostFunction`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/InvokeHostFunctionOpFrame.cpp#L664-L712)). The host converts every entry to host objects at the start of execution, so an entry that cannot be converted fails the operation. It checks signatures, nonces and expiration only for an entry that a `require_auth` call matches, and nothing checks that every entry was used ([`require_auth_enforcing`](https://github.com/stellar/rs-soroban-env/blob/v30.0.0/soroban-env-host/src/auth.rs#L1227-L1295), [`maybe_authorize_invocation`](https://github.com/stellar/rs-soroban-env/blob/v30.0.0/soroban-env-host/src/auth.rs#L2474-L2520)). An entry that no call matches can name any address with any signature and still appear in a successful transaction. Source-account credentials carry no signature at all and rest on the transaction signatures ([`authenticate`](https://github.com/stellar/rs-soroban-env/blob/v30.0.0/soroban-env-host/src/auth.rs#L2665-L2720)).

**Contract call arguments.** Core checks only that the envelope parses within the XDR depth limit and fits the transaction size limit. The host converts arguments when it runs the call and fails the operation on a map whose keys are not strictly sorted ([`validateXDRForProtocol`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/TransactionUtils.cpp#L1349-L1380), [`MeteredOrdMap::from_map_with_host`](https://github.com/stellar/rs-soroban-env/blob/v30.0.0/soroban-env-host/src/host/metered_map.rs#L324-L346)). A failed invocation can therefore carry unsorted or colliding map keys.

**Assets, claimants and names.** From protocol 13 a payment or path payment does not check that the asset issuer exists, and the field table lists the same for other operations ([`PathPaymentOpFrameBase::checkIssuer`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/PathPaymentOpFrameBase.cpp#L76-L90)). Claimable balance claimants must be unique within the operation but need not exist ([`CreateClaimableBalanceOpFrame::doCheckValid`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/CreateClaimableBalanceOpFrame.cpp#L263-L298)). Home domains and data entry names must be printable ASCII, and nothing more ([`isStringValid`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/util/types.cpp#L105-L116)).

### Ordering rules

**Liquidity pool assets order by raw bytes.** A pool-share trustline requires `assetA < assetB` ([`isPoolShareAssetValid`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/util/types.cpp#L132-L144)). The comparison is by asset type, then the asset code as raw bytes including zero padding, then the issuer as its raw 32 key bytes, and a pair in the wrong order fails with `CHANGE_TRUST_MALFORMED`. Strkey text order is different: base32 uses the digits `2` to `7` for its highest values, 26 to 31, but in ASCII they sort before `A` to `Z`. With the same asset code, an issuer of 32 zero bytes (`GAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAWHF`) comes first by bytes, while an issuer of 32 bytes of `0x3a` (`GA5DUOR2HI5DUOR2HI5DUOR2HI5DUOR2HI5DUOR2HI5DUOR2HI5DVTUJ`) comes first as text. js-stellar-sdk before version 17.2.1 sorted issuers as text and rejected valid pairs ([js-stellar-sdk#1766](https://github.com/stellar/js-stellar-sdk/pull/1766)).

**`ScMap` keys order by the Soroban host's comparison, not by XDR bytes.** The host requires map keys to be strictly increasing ([`from_map_with_host`](https://github.com/stellar/rs-soroban-env/blob/v30.0.0/soroban-env-host/src/host/metered_map.rs#L324-L346)). Its comparison orders values of different types by their `ScValType` discriminant, then compares bytes, strings and symbols bytewise, vectors and maps element by element, and numbers by value ([`Compare<ScVal>`](https://github.com/stellar/rs-soroban-env/blob/v30.0.0/soroban-env-host/src/host/comparison.rs#L298-L378)). XDR byte order differs: a length prefix puts symbol `"b"` before `"aa"`, and two's complement puts `-1` after `1` ([js-stellar-sdk#1766](https://github.com/stellar/js-stellar-sdk/pull/1766), [RFC 4506 section 4.1](https://www.rfc-editor.org/rfc/rfc4506#section-4.1), [section 4.11](https://www.rfc-editor.org/rfc/rfc4506#section-4.11)). In host order, symbols `b, aa, a` sort to `a, aa, b`, i128 keys `1, -1, 0, -200` sort to `-200, -1, 0, 1`, and bytes keys `[10], [9], [1,2], [2]` sort to `[1,2], [2], [9], [10]`. Use this order in any code that builds, re-encodes or checks a map.

### Signatures and hints {#signatures-and-hints}

**A signed-payload signature is not bound to a network or a transaction.** For a signed-payload signer core verifies an ed25519 signature over the raw payload bytes, with no network ID and no hashing ([`verifyEd25519SignedPayload`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/SignatureUtils.cpp#L48-L61)). A transaction signature, by contrast, signs a hash of the network ID, the envelope type and the transaction ([`TransactionFrame::getContentsHash`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/TransactionFrame.cpp#L153-L180)). The same signed-payload signature therefore satisfies the same signer on every network and in every transaction that lists it.

**Hints are a filter, not an identity.** Core tries a signer only when the 4-byte hint of a signature matches it ([`SignatureUtils::verify`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/SignatureUtils.cpp#L38-L46)). For a signed-payload signer the expected hint is the last 4 bytes of the ed25519 key XORed with a 4-byte hint of the payload ([`getSignedPayloadHint`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/SignatureUtils.cpp#L93-L105)). The payload hint is the last 4 payload bytes when the payload has 4 or more bytes; a payload of 1 to 3 bytes is copied into the start of the hint instead ([`getHint`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/SignatureUtils.cpp#L107-L125)). Two signers can share a hint, so never attribute a signature to a signer by its hint.

### Soroban memo and muxed source rule

From protocol 25 core rejects with `txSOROBAN_INVALID` a transaction whose single `INVOKE_HOST_FUNCTION` operation comes with a memo, a muxed transaction source or a muxed operation source ([`TransactionFrame::validateSorobanMemo`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/TransactionFrame.cpp#L340-L369), [`TransactionFrame::commonValidPreSeqNum`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/TransactionFrame.cpp#L1315-L1328)). Before protocol 25 the same check exists only as an admission policy of a node's transaction queue ([`TransactionQueue::canAdd`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/herder/TransactionQueue.cpp#L498-L507)), which is not a consensus rule, so ledgers before protocol 25 can contain Soroban invocations with a memo or a muxed source. Extend and restore transactions are not covered by the rule.

## Recommended caps {#recommended-caps}

Each cap below, except the serving limit `state_changes.per_tx.query`, equals the tightest bound the network itself guarantees for the data in its "Applies to" column, so applying it to that data never refuses anything core could have put in a ledger. Apply each cap only to that data: `scval.depth` covers values in transaction meta, and arguments in an envelope have their own, larger cap, `scval.depth.envelope`. A value above a cap is malformed or hostile input, unless the cap is marked "network setting" and validators have since changed that setting.

The bounds that matter most:

- **Envelope depth.** From protocol 28 core rejects with `txMALFORMED` any envelope that its Rust XDR parser cannot read at depth 1000. Before protocol 28 it used a depth check of 500 in its C++ XDR library ([`validateXDRForProtocol`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/TransactionUtils.cpp#L1349-L1380)).
- **ScVal depth.** The Soroban host does not produce values nested deeper than `DEFAULT_HOST_DEPTH_LIMIT`, 100 ([limits.rs](https://github.com/stellar/rs-soroban-env/blob/v30.0.0/soroban-env-host/src/budget/limits.rs#L41)). Arguments in an envelope are bounded only by the envelope depth, so a failed transaction can carry deeper ones.
- **Authorization trees.** The host converts declared invocation trees without a depth limit ([`AuthorizedInvocation::from_xdr`](https://github.com/stellar/rs-soroban-env/blob/v30.0.0/soroban-env-host/src/auth.rs#L813-L826)). Only the envelope depth and size bound them, which allows a single chain of 493 levels and up to 2540 invocation nodes in one transaction (`auth.invocation.depth` and `auth.invocation.nodes` below).
- **Unbounded XDR vectors.** `SCVec`, `SCMap`, `SCBytes`, `SCString`, authorization entry lists and sub-invocation lists have no XDR length bound ([Stellar-contract.x](https://github.com/stellar/stellar-xdr/blob/v30.0/Stellar-contract.x), [Stellar-transaction.x](https://github.com/stellar/stellar-xdr/blob/v30.0/Stellar-transaction.x)). Their caps below are derived from the transaction size limit.

Decoders differ in what they do by default. rs-stellar-xdr decodes with the `Limits` the caller passes, and `Limits::none()` turns off both the depth and the length limit ([generated.rs](https://github.com/stellar/rs-stellar-xdr/blob/v30.0.0/src/generated.rs#L353-L382)). go-xdr, which go-stellar-sdk uses, defaults to a depth limit of 1500 and caps slice preallocation at 256 elements ([decode.go](https://github.com/stellar/go-xdr/blob/dc590f17552a5063bc59411b7e6b9e928b852435/xdr3/decode.go#L35-L45)). Whatever the language, pass the caps below explicitly.

Caps marked "network setting" come from `CONFIG_SETTING` ledger entries that validators can change by vote. The values shown were read from testnet and mainnet on the date listed; read the current values from the network rather than hardcoding them.

### When a value is refused {#when-a-value-is-refused}

A decoder can refuse a value that is in a ledger, and so can a cap that is applied to the wrong data or that comes from a network setting validators have raised. SDKs add refusals as they fix bugs: from version 17.3.0, js-stellar-sdk's `scValToNative()` throws a `TypeError` when two keys of an `scvMap` convert to the same object property, and its release notes say that `humanizeEvents()` and contract-client decoding can now throw on data read from the network, because any contract can emit such a map ([v17.3.0 release notes](https://github.com/stellar/js-stellar-sdk/releases/tag/v17.3.0), [js-stellar-sdk#1789](https://github.com/stellar/js-stellar-sdk/issues/1789)).

Without a plan for refusals, one value can halt an indexer. In wallet-backend, a `SetOptions` operation that added a signed-payload signer made the database copy fail, the persist rolled back together with the cursor, and ingestion retried the same ledger forever ([wallet-backend#729](https://github.com/stellar/wallet-backend/pull/729)). A muxed Soroban source and its base account produced a duplicate key that stopped ingestion at that ledger after every restart ([wallet-backend#753](https://github.com/stellar/wallet-backend/pull/753)). A muxed contract address failed the whole ledger persist ([wallet-backend#792](https://github.com/stellar/wallet-backend/pull/792)). stellar-etl has an open request for a documented policy for non-conforming events ([stellar-etl#467](https://github.com/stellar/stellar-etl/issues/467)).

Decide the policy before it is needed, and test it:

- **Skip and count** a single value that exceeds a cap or that a decoder refuses: store the rest of the transaction, record what was skipped and why, and expose the count as a metric.
- **Quarantine and continue** a transaction that cannot be stored: write it, with the error, to a quarantine table, store the rest of the ledger, advance the cursor, and alert. Reprocess quarantined transactions after a fix.
- **Halt** only when the ledger itself cannot be read, for example when a `LedgerCloseMeta` fails to decode within the caps, because skipping it would leave a silent gap.

## Participants from meta, not from the envelope {#participants-from-meta}

The envelope names who a transaction meant to involve. Transaction meta records which ledger entries actually changed. A participant set built from the envelope goes wrong in four ways:

- **It includes accounts that were never touched.** A failed transaction is still in the ledger with every account its envelope names. Claimants of a claimable balance need not exist ([`CreateClaimableBalanceOpFrame::doCheckValid`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/CreateClaimableBalanceOpFrame.cpp#L263-L298)), footprint keys need not exist, and a declared authorization entry that no call matched was never checked (see the field table).
- **It misses accounts that were touched.** The Stellar Asset Contract's `trust` function creates a trustline without emitting an event, and an XLM transfer through it can create an account ([CAP-73](https://github.com/stellar/stellar-protocol/blob/master/core/cap-0073.md)). Contract calls change balances and data of accounts and contracts that no envelope field names.
- **It names the same account twice.** A muxed source and its base `G` account are one account ([`toAccountID`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/TransactionUtils.cpp#L1184-L1201)). Keeping both as participants produced the duplicate key in [wallet-backend#753](https://github.com/stellar/wallet-backend/pull/753).
- **It treats declared intent as a fact.** wallet-backend emitted contract-creation state changes from declared authorization entries whether or not the deployment ran ([wallet-backend#746](https://github.com/stellar/wallet-backend/issues/746)), and later moved Soroban participants to executed meta ([commit 9538b3c](https://github.com/stellar/wallet-backend/commit/9538b3caeaebfeb3d034146c0ce9643c3066cf8a)).

Every change to the ledger is in one of these places ([Stellar-ledger.x](https://github.com/stellar/stellar-xdr/blob/v30.0/Stellar-ledger.x#L493-L596)):

- `feeProcessing` in each transaction's result meta: the fee charge, which happens even when the transaction fails.
- `txChangesBefore`, the changes of each operation, and `txChangesAfter` in `TransactionMeta`.
- `postTxApplyFeeProcessing` in `TransactionResultMetaV1`: Soroban fee refunds from protocol 23.
- Events: contract events, and from `TransactionMetaV4` (protocol 23) the per-operation events and the transaction-level fee events of [CAP-67](https://github.com/stellar/stellar-protocol/blob/master/core/cap-0067.md).

Read all of them. In go-stellar-sdk, `LedgerTransaction.GetChanges()` returns the transaction and operation changes but not the fee changes, which come from `GetFeeChanges()` and `GetPostApplyFeeChanges()` ([ledger_transaction.go](https://github.com/stellar/go-stellar-sdk/blob/v0.9.0/ingest/ledger_transaction.go#L48-L92)).

To build a transaction's participant set:

1. Take the owner of every ledger entry that changed in the places above, keyed by base account (`G`), contract (`C`), liquidity pool (`L`) or claimable balance (`B`).
2. Add the addresses in event topics and data, reduced to their base account or contract, with mux ids recorded separately.
3. Keep envelope accounts that do not appear in meta, if you need them, in a separate "declared" set, and never merge the two.

## Muxed and signed-payload addresses {#muxed-and-signed-payload-addresses}

### Strkey forms

[SEP-23](https://github.com/stellar/stellar-protocol/blob/master/ecosystem/sep-0023.md) defines ten strkey forms. The first character is set by the top 5 bits of the version byte; the low 3 bits select the algorithm, ed25519 or SHA-256, both 0 today. The binary form is the version byte, the payload, and a 2-byte CRC16 checksum, encoded as base32 without padding.

| Prefix | SEP-23 type | Version byte | Payload | Where it appears in ledger data | How to store it |
| --- | --- | --- | --- | --- | --- |
| `G` | `STRKEY_PUBKEY` | `6 << 3` | 32-byte ed25519 public key | `AccountID`, the plain arm of `MuxedAccount`, ed25519 signer keys, account `ScAddress` | 32 key bytes with the key type |
| `M` | `STRKEY_MUXED` | `12 << 3` | 32-byte ed25519 key, then 8-byte id, most significant byte first | `MuxedAccount` ([CAP-27](https://github.com/stellar/stellar-protocol/blob/master/core/cap-0027.md), protocol 13), muxed account `ScAddress` ([CAP-67](https://github.com/stellar/stellar-protocol/blob/master/core/cap-0067.md), protocol 23) | base `G` key, and the id as an unsigned 64-bit value in its own column |
| `S` | `STRKEY_PRIVKEY` | `18 << 3` | 32-byte ed25519 secret seed | a secret key, used to sign | never store; treat one in ledger-derived data as a bug |
| `T` | `STRKEY_PRE_AUTH_TX` | `19 << 3` | 32-byte transaction hash | pre-authorized transaction signer keys | signer column, with the key type |
| `X` | `STRKEY_HASH_X` | `23 << 3` | 32-byte SHA-256 hash | hash-x signer keys | signer column, with the key type |
| `P` | `STRKEY_SIGNED_PAYLOAD` | `15 << 3` | 32-byte ed25519 key, 4-byte payload length, 1 to 64 payload bytes, zero padding to a multiple of 4 | signed-payload signer keys ([CAP-40](https://github.com/stellar/stellar-protocol/blob/master/core/cap-0040.md), protocol 19) | signer column wide enough for the whole payload |
| `C` | `STRKEY_CONTRACT` | `2 << 3` | 32-byte contract id | contract `ScAddress`, `ContractID` | 32 bytes with the address type |
| `L` | `STRKEY_LIQUIDITY_POOL` | `11 << 3` | 32-byte pool id | `PoolID`, liquidity pool `ScAddress` (CAP-67) | 32 bytes with the address type |
| `B` | `STRKEY_CLAIMABLE_BALANCE` | `1 << 3` | 1-byte balance id type (0 for V0), then 32-byte hash | `ClaimableBalanceID`, claimable balance `ScAddress` (CAP-67) | 33 bytes, type byte included |
| `W` | `STRKEY_MUXED_CONTRACT` | `22 << 3` | 32-byte contract id, then 8-byte id, most significant byte first | muxed contract `ScAddress` ([CAP-84](https://github.com/stellar/stellar-protocol/blob/master/core/cap-0084.md), protocol 30) | contract `C` id, and the id as an unsigned 64-bit value in its own column |

The XDR types behind these forms are `MuxedAccount` ([Stellar-transaction.x](https://github.com/stellar/stellar-xdr/blob/v30.0/Stellar-transaction.x#L21-L31)), `SignerKey` ([Stellar-types.x](https://github.com/stellar/stellar-xdr/blob/v30.0/Stellar-types.x#L61-L79)), `PoolID` and `ClaimableBalanceID` ([Stellar-types.x](https://github.com/stellar/stellar-xdr/blob/v30.0/Stellar-types.x#L142-L153)) and `SCAddress` with its six address types ([Stellar-contract.x](https://github.com/stellar/stellar-xdr/blob/v30.0/Stellar-contract.x#L179-L215)).

SEP-23 requires decoders to reject a strkey that does not re-encode to the same string, including lengths congruent to 1, 3 or 6 mod 8, nonzero unused bits and padding characters. SEP-23 names Go's `base32.StdEncoding.WithPadding(base32.NoPadding)` as a base32 decoder that accepts those inputs, so check them yourself or round-trip every decoded strkey.

### Storing muxed addresses

**Store the base account and the mux id separately.** Core never validates or stores a mux id (see [Fields core never checks](#fields-core-never-checks)), so the account that exists on the ledger is the `G` key. Key balances, trustlines and participants by the base key, and keep the id in a separate column. The id is an unsigned 64-bit value: the SEP-23 test vectors include id 9223372036854775808, above the largest signed 64-bit integer. Store it as an unsigned 64-bit integer or a decimal string. wallet-backend stores it as a decimal string so that ids above 2^63-1 round-trip ([`toMuxedIDValue`](https://github.com/stellar/wallet-backend/blob/3e22515a44979fdc3a558fda3991ca2b48e38cef/internal/indexer/processors/state_change_builder.go#L140-L144)).

**Never truncate.** An `M` or `W` payload is 40 bytes. Fitting it into a 32-byte column either fails the write or silently produces rows that do not decode back ([wallet-backend#716](https://github.com/stellar/wallet-backend/issues/716)). wallet-backend now reduces `M` and `W` addresses to their 32-byte base key and rejects any other payload length rather than truncating it ([`AddressBytea.Value`](https://github.com/stellar/wallet-backend/blob/3e22515a44979fdc3a558fda3991ca2b48e38cef/internal/indexer/types/types.go#L76-L116)).

**Build strkeys from parsed fields, not from XDR bytes.** XDR puts the id first: `MuxedAccount` has `{ id, ed25519 }` and `MuxedContract` has `{ id, contractId }`. The strkey payload puts the key first and the id last. Copying the XDR bytes into a strkey yields a valid-looking address for the wrong key.

**Read the destination id of a transfer from its event.** From protocol 23 classic and Stellar Asset Contract transfer and mint events carry the destination's id in a `to_muxed_id` field of the event data ([CAP-67](https://github.com/stellar/stellar-protocol/blob/master/core/cap-0067.md)), and from protocol 30 a transfer to a `W` address carries the contract as the destination and the id in `to_muxed_id` ([CAP-84](https://github.com/stellar/stellar-protocol/blob/master/core/cap-0084.md)). For a classic payment to a plain `G` account the same field holds the transaction memo instead, as a string, a u64 or bytes ([`makeClassicMemoSCVal`](https://github.com/stellar/stellar-core/blob/v30.0.0/src/transactions/TransactionUtils.cpp#L2252-L2270)), so check its type before treating it as an id.

### Storing signed-payload signers

**Store the full payload with its length.** In strkey form a signed-payload key is a 32-byte ed25519 key, a 4-byte length and 1 to 64 payload bytes padded to a multiple of 4, 40 to 100 bytes in all, so it does not fit an account column. wallet-backend stores signer keys as the version byte plus the full payload, 33 bytes for `G`, `T` and `X` keys and up to 101 bytes for `P` keys, and rejects any other key type in a signer column ([`SignerKeyBytea`](https://github.com/stellar/wallet-backend/blob/3e22515a44979fdc3a558fda3991ca2b48e38cef/internal/indexer/types/types.go#L191-L252), [wallet-backend#729](https://github.com/stellar/wallet-backend/pull/729)). Two `P` signers over the same ed25519 key with different payloads are different signers, and both differ from the plain `G` signer of that key.

**Do not treat a signed-payload signature as transaction-specific.** It signs only the payload (see [Signatures and hints](#signatures-and-hints)), so the same signature can authorize transactions on any network.

**Take signer sets from meta.** A `SetOptions` signer and a revoked signer sponsorship are requests that can fail, and an extra signer in preconditions never becomes an account signer. The account entry in meta shows the signers an account has.

## Self-audit checklist {#self-audit-checklist}

Use this list to review an indexer in any language. The first three items are the rules of [indexerlint](https://github.com/ErenTopaal/shapekit/blob/v0.1.0/docs/linter.md), the shapekit analyzer for Go indexers built on go-stellar-sdk, with the rule IDs and wording it prints.

{/* shapekit:begin checklist */}

- [ ] `IDX001` `unvalidated-field-trusted`: a transaction field that stellar-core does not validate is trusted without a check. Before you store, key, display or convert to text any field listed as not validated in the field table, validate it yourself (length, encoding, range) or confirm it against what the transaction meta and events say actually happened.
- [ ] `IDX002` `missing-depth-or-size-cap`: a recursive or length-prefixed xdr structure is walked or decoded without a depth or size cap. Decode external XDR with an explicit depth limit and a length limit no larger than the input buffer, carry a depth counter through every recursive walk of ScVal, auth invocation and claim predicate trees, and check each decoded length against the cap in the caps table before allocating or iterating.
- [ ] `IDX003` `participants-from-envelope`: participants are derived from the transaction envelope instead of meta changes or events. Build each transaction's participant set from the ledger entry changes (fee changes included) and events in its meta, and treat accounts named only in the envelope as declared intent, not participation.
- [ ] **Muxed accounts are stored as a base account plus an id.** Every M address is reduced to its 32-byte G key for account identity, and its 64-bit id is kept in a separate unsigned 64-bit column or as a decimal string. No column truncates an M address to 32 bytes. Fields: `tx.source_account.mux_id`, `op.source_account.mux_id`, `feebump.fee_source.mux_id`, `op.payment.destination.mux_id`, `op.path_payment.destination.mux_id`, `op.clawback.from.mux_id`. Sources: [SEP-23](https://github.com/stellar/stellar-protocol/blob/master/ecosystem/sep-0023.md), [wallet-backend#716](https://github.com/stellar/wallet-backend/issues/716).
- [ ] **Muxed contract (W) addresses are handled.** From protocol 30 an ScAddress can be a muxed contract. Its contract id (C) and its 64-bit id are stored separately, and a W address anywhere in events or arguments does not fail the ledger. Sources: [CAP-84](https://github.com/stellar/stellar-protocol/blob/master/core/cap-0084.md), [wallet-backend#792](https://github.com/stellar/wallet-backend/pull/792).
- [ ] **Signer keys keep their type and full payload.** Signer columns store the key type with the key, and are wide enough for a signed-payload (P) key with a 64-byte payload. Signers are never stored in an account column. Fields: `signer_key.signed_payload.payload`, `op.set_options.signer`, `tx.cond.extra_signers`, `op.revoke_sponsorship`. Caps: `signer.signed_payload.len`. Sources: [wallet-backend#729](https://github.com/stellar/wallet-backend/pull/729).
- [ ] **Strkeys and textual ids are decoded strictly.** Strkey decoding rejects every form SEP-23 lists as invalid, and a textual mux id or offer id is accepted only in its canonical decimal form. Fields: `tx.source_account.mux_id`, `op.manage_offer.offer_id`. Sources: [SEP-23](https://github.com/stellar/stellar-protocol/blob/master/ecosystem/sep-0023.md), [js-stellar-sdk#1785](https://github.com/stellar/js-stellar-sdk/issues/1785).
- [ ] **64-bit ids stay exact.** Mux ids and memo ids are unsigned 64-bit values and can exceed 2^63-1. They are not stored in signed 64-bit columns or converted to floating point numbers, and amounts are never stored as floats. Fields: `tx.memo.id`, `tx.source_account.mux_id`, `op.manage_offer.offer_id`, `op.payment.amount`.
- [ ] **Memo text is stored as bytes.** MEMO_TEXT is kept as its raw bytes (at most 28). If a text form is needed, UTF-8 is validated explicitly and the raw bytes are kept alongside it. Fields: `tx.memo.text`. Caps: `tx.memo_text.len`. Sources: [js-stellar-sdk#1823](https://github.com/stellar/js-stellar-sdk/issues/1823).
- [ ] **Ordering follows the network's rules.** Liquidity pool assets are ordered by asset type, raw code bytes and raw issuer key bytes, never by strkey text. Code that sorts or checks ScMap keys uses the Soroban host's ScVal comparison, not string order and not XDR byte order. Fields: `op.change_trust.line.liquidity_pool`, `op.invoke_host_function.invoke_contract.args`. Sources: [js-stellar-sdk#1766](https://github.com/stellar/js-stellar-sdk/pull/1766).
- [ ] **Failed transactions are not treated as effects.** An envelope value is only treated as having taken effect when the transaction result and the operation result are successes. For a failed transaction only the fee changes in meta are recorded as effects. Fields: `tx.signatures`, `op.payment.destination`, `op.invoke_host_function.invoke_contract.contract_address`.
- [ ] **Caps are applied when decoding.** Every XDR decode of external input sets an explicit depth limit and a length limit no larger than the input buffer, using the caps in the table. A decoder is never run with its limits turned off. Caps: `xdr.envelope.depth`, `xdr.envelope.len`, `xdr.meta.depth`, `xdr.meta.len`.
- [ ] **Serving limits stay at query time.** Limits that protect an API, such as rows per transaction on a history page, are applied when serving. Ingestion stores every row. Caps: `state_changes.per_tx.query`.
- [ ] **Caps that come from network settings are re-read.** Caps marked as network settings are read from the CONFIG_SETTING ledger entries the network currently uses, not hardcoded, because validators can change them by vote. Caps: `xdr.envelope.len`, `soroban.footprint.entries`, `soroban.contract_data.entry_bytes`, `events.contract.bytes_per_tx`.
- [ ] **There is a written refusal policy.** For every place a decoder can throw or a value can exceed a cap, the indexer has a tested, documented choice: skip the value and count it, quarantine the transaction, or halt. Nothing is dropped without being counted, and SDK upgrades are checked for new refusals. Sources: [js-stellar-sdk 17.3.0 release notes](https://github.com/stellar/js-stellar-sdk/releases/tag/v17.3.0), [stellar-etl#467](https://github.com/stellar/stellar-etl/issues/467).
- [ ] **One poison transaction cannot stop ingestion.** When a single transaction cannot be stored, the indexer records it in a quarantine with the error, stores the rest of the ledger, advances the cursor and alerts, instead of retrying the same ledger forever. Sources: [wallet-backend#729](https://github.com/stellar/wallet-backend/pull/729), [wallet-backend#753](https://github.com/stellar/wallet-backend/pull/753).
- [ ] **Soroban invocations before protocol 25 can carry a memo or a muxed source.** Code that handles INVOKE_HOST_FUNCTION transactions accepts a memo and muxed source accounts in ledgers before protocol 25, where the rule was only a transaction queue policy. Fields: `tx.memo.type`, `tx.source_account.mux_id`, `op.source_account.mux_id`.
